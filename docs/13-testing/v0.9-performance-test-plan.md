# v0.9 Performance Test Plan

## Objectives

- Produce machine-readable, repeatable HTTP baseline evidence.
- Exercise success, non-2xx, timeout, connection failure, and oversized-body
  classifications.
- Verify hard bounds on request count, concurrency, timeout, warmups, and body
  size.
- Keep private-network targets opt-in and prevent sensitive response data from
  entering evidence.

## Automated Tests

`python/tests/test_performance_benchmark.py` uses deterministic response doubles
and a local loopback HTTP fixture. It covers URL validation, private-network
opt-in, all parameter bounds, pinned transport, parallel execution, JSON
contract, status classification, timeout, connection failure, HTTP error status
retention, the versioned result schema, and the P99 pass/fail gate.
The suite collects 25 pytest cases after parameterized boundary expansion.
On Python 3.12.14 the focused suite passed all 25 cases and recorded 86% total
coverage (`run_benchmark.py` 85%, `local_fixture.py` 92%).

Run the focused suite with:

```bash
cd python
pytest tests/test_performance_benchmark.py --no-cov
```

The same focused command is a required CI step. It must pass independently of
coverage instrumentation because the benchmark contract is a release gate.

The focused module coverage gate is run in CI with:

```bash
python -m coverage run --source=../benchmark -m pytest tests/test_performance_benchmark.py --no-cov
python -m coverage report --fail-under=80
```

Ruff formatting/lint and strict Mypy explicitly include `benchmark/`; the
standard Python working-directory checks alone do not cover this top-level
module.

## Local Baseline Procedure

Start the repository's deterministic fixture, then explicitly opt in to the
private target:

```bash
python3 benchmark/local_fixture.py --host 127.0.0.1 --port 8000
```

In a second terminal run:

```bash
./benchmark/run-benchmark.sh http://127.0.0.1:8000/health docs/13-testing/results/v0.9-performance-baseline.json \
  --allow-private-network --requests 200 --concurrency 4 --warmups 10 --timeout 2 --max-p99-ms 100
```

The resulting JSON must be reviewed with the commit SHA, service version,
hardware, fixture configuration, and timestamp. A failed request makes the
result `FAIL` and must be investigated before release.

The current implementation evidence is bound to commit `40364d0`: 200/200
successful requests, four-way concurrency, zero errors, and P99 28.553 ms
against a 100 ms threshold on Python 3.12.14.

## Release Evidence

This harness is control-plane evidence only. v0.9.0-alpha cannot claim HA,
automatic scaling, production capacity, multi-node recovery, or chaos
resilience until those tests run against the intended deployment topology and
their results are attached to a release checklist.

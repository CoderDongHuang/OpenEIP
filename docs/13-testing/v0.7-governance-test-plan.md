# v0.7 Governance Test Plan

> Issue: #99 | Coverage gate: >= 80% per changed module

## Runtime quota enforcement slice

| Area | Required evidence |
|---|---|
| Domain | bounded non-negative reservations, bounded idempotency key, valid lease interval, UTC window calculation |
| Admission | token/cost/request/concurrency limits, exact-boundary allow, exceeded-dimension deny, stable `GOV-B-001` |
| Idempotency | identical retry returns original decision; changed facts return `GOV-I-001` without a second row |
| Lifecycle | release is tenant-scoped and idempotent; released/expired leases stop reserving capacity; requests remain counted |
| Isolation | policy lookup, decision query, release, usage aggregation, and audit cannot cross tenant boundaries |
| Concurrency | competing transactions against one policy cannot exceed concurrency or request limits |
| Migration | MySQL forward migration creates tenant-leading keys and foreign keys; rollback removes the added table safely |
| Compatibility | existing v0.1-v0.6 API/SPI tests and all Java module gates remain unchanged and passing |

## Benchmark

The deterministic benchmark executes 1,000 sequential admissions and 100 competing admissions against H2 using
the production JDBC adapter. The local gate is sequential admission P99 below 50 ms, zero unexpected decisions,
and no duplicate decision rows. This measures control-plane overhead only; it is not a production capacity claim
for MySQL, providers, Agent execution, or distributed deployment.

## Security evidence

Tests must cover cross-tenant policy IDs, expired context, stale policy version, oversized idempotency keys,
negative requested values, replay with changed facts, lease expiry, and concurrent oversell. Audit summaries and
quota rows contain identifiers, bounded counts, decisions, and correlation metadata only; they never contain
Prompt text, credentials, Tool values, provider payloads, or private reasoning.
